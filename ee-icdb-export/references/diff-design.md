# ECO 比对的设计决策与实测记录

`--diff` 为什么这么设计。SKILL.md 只留结论与入口，推理过程放这里。

## 1. 以位号为键，不以料号为键

位号是板上的物理位置。"同一位置换了料"正是 ECO 复核要抓的事，所以元件层严格
按位号比对。若按料号比对，这件事会被稀释成"某料号用量变了"，看不出换了什么。

| 分类 | 规则 |
|---|---|
| 更换料号 | 位号相同、料号不同 |
| 变更参数 | 位号与料号都相同，Value / Value1 / Part Name 有变 |
| 新增元件 | 位号只在新版存在 |
| 删除元件 | 位号只在旧版存在 |

## 2. 故意不计入判定的两个属性

- **Cell Name（属性号 15）**。在真实工程上实测：该工程的 Cell Name 与 Part Name
  取同一个值，且只有一端填了。纳入判定会多出 7 行 `(空) -> XXX`，那是属性补录、
  不是电气变更 —— 去掉后差异从 20 降到 13，而这 13 条条都是真差异。真正的封装变
  更必然同时动 Part Name 或料号，所以不纳入也不会漏。原始值仍印在明细报告里。
- **图纸页（Sheet page）**。纳入判定的话，图纸重新编号就会把报告灌满噪声。
  图纸名仍出现在明细报告里，供人工核对。

## 3. 多单元件与空值

一个位号下挂多个符号（U1A/U1B）时，按**多重集**比对而非逐行配对，这样单元数变化
会被报出来，而不是被静默地一一对齐掉。

空属性值渲染为 `(空)`：若把空串丢掉，`{"", "U1"}` 与 `{"U1"}` 会看起来一样，
差异就被藏掉了。

## 4. 网络层：以引脚为键，不以网络名为键

元件层看不出"新增的元件接在哪里"，而这恰恰是真实 ECO 里更有意思的那半。

比对对象是 `work\database.ppn`（扁平网表的物理引脚视图），一行一个引脚，
带它所在的网络。

**主轴是 `(位号, 引脚) → 网络`**：同一根脚换到别的网络，就是一次改接。
网络名不能当键，因为 EE 会自动生成 —— 本工程有 100 个形如 `<AUTO_NET>` 的网络，
符号顺序一变就重新编号。以引脚为键在构造上就免疫这件事：重编号不会移动任何引脚。

若改用网络名当键，同一件事还会被拆成两行互不相关的记录：`<D1>.1` 离开
`<NET_CTRL>` 去了一个全新网络，会读成"那个网络少了一根脚"**加上**"多了一个
网络"，真正的意图反而看不见了。

| 分类 | 含义 |
|---|---|
| 引脚改接 | 位号与引脚相同、网络不同 —— **唯一计入合计的** |
| 新增接点 / 断开接点 | 只在单侧存在的引脚 —— 属背景信息，一行一根脚 |
| 网络构成变化 | 两侧都有、但引脚集合不同 |
| 网络改名 | 未配对的网络按端点重合度配对成功 —— 是改名，不是删+增 |
| 新增网络 / 删除网络 | 另一侧没有对应物 |
| 命名漂移 | 自动命名的网络被重编号、但连接完全相同 —— **不算变化** |

只有**引脚改接**计入网络层合计。网络层的其余行是同一批事件的另一个视角，正如
"受影响料号"是元件变更的另一个视角 —— 相加就是重复计数。

改名配对用端点集合的 Jaccard 重合度（≥ 0.5），这样一个被改名的网络得到一行，
而不是"删除 + 新增"两行。当未配对的两个网络**端点集合完全相同**且两个名字都是
自动生成的时候，那是记账不是 ECO：计为**命名漂移**，不进差异行，但仍列出来，
不隐藏任何东西。

## 5. 报告形态上的三条权衡

**为什么工作表要分开。** 它替代的那张单表把四层塞在同一个 `分类` 列后面，这正
是它难读的原因：四种互不兼容的行形状共用一个表头，按任何一列排序都会打乱其他列，
筛选还会命中读者根本没在看的那几层。一层一张表，每张表的列才能各自成立。

**工作簿是字段级，网页是对象级。** 一个位号改了两处，在 Excel 里就是两行 ——
这样"变更项"这一列才能筛选（点一下"料号"就看到所有换料）。网页上一个位号只占
一行，只显示真正移动了的字段。新增元件在两个报告里都不是"四个参数挤在一格"：
工作簿和 CSV 会把它摊成一行一个字段。**两种格式的行数本来就不同**，它们回答的
不是同一个问题。

**行数可以对账。** 拿工作簿和 CSV 互校是个值得跑的自检：元件行数必须相等，
引脚与料号同理。网络行数只能相等或 CSV 更多 —— 一个既丢脚又加脚的网络在 CSV 里
是两行，在工作簿里是一行。

**`.xlsx` 不依赖第三方包。** `xlsx_writer.py` 用 `zipfile` 加字符串模板写出工作
簿 —— .xlsx 就是 XML 的 zip，Excel 和 WPS 都需要的那一小部分子集并不大。因此报告
在既没有 pip 也没有网络的机器上照样能开。这个文件若没被一起拷过去，工具会明说，
并改写 CSV，而不是在最后一步失败。

## 6. 实测记录

`<PROJECT_ID>` vs `<PROJECT_ID>`（一次真实 ECO，元件 468 → 475）：

- 元件层：更换料号 2、变更参数 13、新增 7、删除 0、完全一致 451、
  受影响料号 11 个。每一行都能追到真实改动 —— `/NC` 标记被去掉、一个料号笔误被
  订正（`<PART_NO>` → `-2N`）、<U2> 的一个 Value 被修正。
- 网络层：245 → 249 个网络、1345 → 1360 个连接点。**引脚改接 2**、新增接点 15、
  断开 0、网络构成变化 4、新增网络 4、删除 0、命名漂移 0。

两层合起来描述的是**同一个有意的改动**（一路使能电路返工），任何单独一层都看不
出全貌：

| 证据 | 出自 |
|---|---|
| 新增 7 个元件：<Q1>（MOSFET）、<R1>/26/27/28、<C1>、<R5> | 元件层 |
| `<U1>.88` 从 `<NET_EN>` 移到 `<NET_GPIO>` | 网络层（引脚改接） |
| `<D1>.1` 从 `<NET_CTRL>` 移到 `<AUTO_NET>`，与 `<R5>.2` 并到一处 | 网络层（引脚改接） |
| `<NET_EN>` 增加 `<Q1>.3 <R1>.1 <R2>.2`；`<NET_RAIL>` 增加 `<Q1>.2 <R1>.2 <R4>.2` | 网络层（构成变化） |

即：SOC 的使能脚被改配成 GPIO，使能通路改走一颗 MOSFET，并配了新的上/下拉与
`<C1>` 上的 RC。只看元件层，只会得到一句"多了 7 个料"。

## 7. 自检方法

**零差异自检。** 拿一份导出与它自己比对，必须得到零差异：468 个位号全未变、
CSV 零数据行、每张 HTML 表零数据行（245 个网络完全一致）、工作簿每张表只有一个
表头加一条 `（无差异）`。

**结构自检。** 另外两项检查跑在生成的 HTML 上：每张表的表头单元格数必须与它的行
匹配（当初一个缺失的前导"类型"格就是这样被抓出来的）；有且只有一个区块可以带
初始 `on` 类。第二项的存在是因为 pane 辅助函数的"首个 pane"标志曾被它自己的返回值
覆盖，于是打开时所有区块同时渲染 —— 那正是报告一开始看起来像一堵无边界的表格墙
的原因。

**工作簿回读。** 开发期用 `openpyxl`（仅测试用，永不作为运行依赖）读回工作簿，
确认表名、单元格值、冻结窗格、自动筛选范围和列宽都能往返，且元件 / 引脚 / 料号
的行数与 CSV 一致。同一次检查也验证降级路径：拿掉 `xlsx_writer.py` 之后，工具必须
明说并改写 CSV，而不是失败。

**逐字节回归。** 报告层改动时，用 `SOURCE_DATE_EPOCH=0` 固定产出时间戳，HTML 与
.xlsx 都可以按 sha256 逐字节比对。本工程当前基线：HTML `db57a144fd77a3f5`、
xlsx `71944de00d27566c`。
